## Be aware: what was NOT verified
The code was written in a sandbox with **no access to PyPI, the Android SDK/Maven, Xcode or Swift**, and no Firebase/MongoDB instance. So:
- Backend (Flask port): the pytest suite (15 tests, in-memory repository) was **run and passes** in the sandbox, but with two small stand-ins for `pydantic-settings` and `flask-cors` (PyPI was unreachable, so those two packages could not be installed; Flask, pydantic and pytest were available). `test_mongo_repository.py` was skipped (needs `mongomock`). Never exercised: `gunicorn`, supervisor, real MongoDB/auth, `MinioPhotoStore`, Firebase token verification, FCM.
- Android: Java parsed for syntax only; **never built**. Missing imports or API mismatches are likely on first build.
- iOS: **never compiled** and the Xcode project is generated by `xcodegen` from `project.yml` (not yet run).
- Nothing was run against real Firebase, MongoDB or MinIO (token verification, FCM, GridFS, MinIO photos, reminder job).
- Languages (ar/fr/en) for errors, pushes, notifications, reminder titles and the email, and the FCM payload shape: tested with fakes (18 tests); never seen on a real phone. Arabic and French texts should be proof-read by a native speaker.
- Account deletion (`DELETE /v1/me`) and the public pages (`/privacy`, `/terms`, `/support`, `/delete-account`): tested with an in-memory database and fakes; Firebase `delete_user` never called for real. **The legal texts are templates: the owner (ideally with a lawyer) must review them before the store release** (`app/legal.py`).
- Email verification code: tested with a fake mailer (16 tests); real Mailjet delivery was never tried (tested with a fake Mailjet client).
Plan for the first session: run `pytest`, build both apps, fix compile errors, then do the manual end-to-end checklist in DEVELOPMENT_GUIDE.md.

**Since then (Nov 2026):** from 17 to 24 Nov both apps were compiled on GitHub Actions on every push (stopped on 24 Nov for cost; the last builds passed). What a compiler cannot see (how the screens look and behave on a phone) still needs the checklist in each app's `docs/FEATURE_CHECKLIST.md` (section L for the 18 Nov features). Before that: the backend runs on the VPS against real MongoDB 3.6 and Firebase; Android is built and used by the client. Changes are still written in a sandbox without the Android SDK or Swift compiler: the Java is checked for syntax, duplicate variables and lambda captures, the Swift for translations and documentation only, so **every release must be built in Android Studio and Xcode before it goes to the stores**.

## Backend bug review (membership after sign-in, notifications)

Every real flow (create farm, join, approve, reject, remove, leave, transfer, legacy accounts, sign-out then sign-in) already returned the right `/me` status; scenario tests now prove it (`tests/test_sessions.py`). The backend was not the cause of "the app shows Create/Join farm again after signing in". Weak points found and fixed:

| Problem | Effect | Fix |
|---|---|---|
| `/me` trusted only `users/<uid>`; the member record was not consulted if that pointer was missing or stale | A lost or stale pointer (e.g. data restored from an old backup, a manual edit, an interrupted write) shows "no farm" although the person is a member | The member record is the source of truth: found across farms when needed, and the pointer is repaired |
| `set_user` and `mark_verified` replaced the whole `users` document | Two requests at the same moment (verify email + language update, approve + `/me`) could wipe each other's fields, e.g. the farm | Both now merge only their own fields |
| Push data had no notification id | Tapping a push could not mark its notification read | `data.notification_id` on join requests, approvals and reminders |
| Join-request notifications stayed unread after a decision | Managers kept seeing an unread "X wants to join" | Resolved (read) on approve, reject, cancel or remove, whoever decides |
| Approval was push-only | Nothing in the new member's list | Stored as a personal notification (`for_uid`) |
| `POST /notifications/<id>/read` and `DELETE` did not check visibility | A worker could mark or delete a manager-only join request by id | `404` unless the caller may see it |
| Deleting an account left old rejected/pending member records in other farms | Leftover personal data | All the user's member records are deleted |

## Known gaps / not built
- Launch screens, dark-mode polish on Android custom screens. Server texts are translated (ar/fr/en); the apps' own strings are handled in the app repos.
- Android: few unit tests (sign-up rules, formatting), no UI tests; notification tap opens the app, not the specific animal; photo EXIF rotation not applied.
- iOS: notification tap does not deep-link.
- Offline: lists and record changes work offline; photos, sign-in, farms and members need a connection; changes waiting to be sent do not show in the lists until sent.
- Several farms per account are supported; a person works in one farm at a time (switch in Me > My farms).
- A breed without a free photo on Wikimedia shows the species' photo until a farmer's own photo is copied to the server.
- Finance: no budgets/recurring entries; reports are CSV, plus the monthly finance summary as PDF.
- No in-app feedback form and no crash reporting (Crashlytics), by choice; server errors are in the dashboard's Problems page.
- The API and the dashboard still run on plain HTTP (HTTPS planned later).
- Backend: no rate limiting, no audit log, no pagination beyond `limit`.
- Mockup has no finance, reports, notifications or settings screens (the apps have them).

## Admin: delete a farm (13 Nov 2026)

The apps cannot delete a farm yet (planned, with an admin dashboard). On the server, from the project folder:

- `/home/ubuntu/farmivo/venvfarmivo/bin/python -m scripts.delete_farm` lists the farms (id, name, owner, members, animals); `--find <text>` searches name, id or member email.
- `... -m scripts.delete_farm <farm_id> --dry-run` shows what the farm holds; without `--dry-run` it asks to type the farm name, then deletes the farm, every record under it (including barns) and the animal photos. Members keep their sign-in and get "create or join a farm" in the app. No undo: `mongodump` first if in doubt.
- Fixed at the same time: deleting an account that owns a farm now also deletes the farm's barns (they were left behind); a test checks that every farm collection used in the code is deleted.
